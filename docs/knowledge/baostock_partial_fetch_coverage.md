# baostock 批量取数：中断后必须核对"代码覆盖数"而非行数

## 适用场景
用 baostock 批量拉取多股票历史数据（股本、日线、市值）时，需要判断一次运行是否完整。

## 现象
`bridge/refdata.py shares` 首次运行日志末尾出现 `logout failed!`，进程正常退出，
产物 `shares_pit.parquet` 从 49,965 行 → 50,209 行，**看起来只新增了 244 行**。

若只看行数，很容易得出错误结论："2026 年披露的季度数据本来就少"。

## 根因
baostock 会话约 6-7 分钟过期。会话掉线后循环**静默提前结束**（只拉完前 122 只，
且全部是 00 前缀），但脚本仍在结束时正常落盘，**不报错**。
122 只有效 → 因为"每期只有 122 只"和"每期本该有 3,193 只"在**总行数**上差别不大
（244 行 vs 6,400 行都被淹没在 5 万行里），所以行数不是有效的完整性指标。

## 推荐做法
1. **按"每期/每窗口的代码覆盖数"验收**，不要看总行数：
   ```python
   d[d["stat_date"]=="2026-03-31"]["code"].nunique()   # 应为 3193，而非 122
   ```
2. 发现覆盖不足时，先**单点复查上游是否真有数据**，以区分"取数中断"和"确实未披露"：
   `000544/000545/000546` 单点复查上游均有数据 → 证实是中断。
3. 中断后用同一命令加 `--resume` 续跑。该脚本按 `(code, stat_date)` 跳过已有键，
   因此**续跑幂等安全**；续跑成功时会打印 `logout success!`。
4. 日志尾部的 `logout failed!` 是**中断信号**，出现即应视为本次运行不完整。

## 验证依据
2026-10-17 实测：首次 50,209 行 / 每期 122 只 → `--resume` 续跑后 56,372 行 /
每期 3,193 只（3,194 只中仅 1 只缺），`(code,stat_date)` 零重复、
`pub_date ≥ stat_date` 零违例。

## 适用边界
- baostock 会话过期机制所致，与项目代码无关。
- 同类风险：任何"循环取数 + 结束才落盘"的批量脚本，中断都会丢全部进度
  （`_s1_mc_fetch.py` 同样只在全批结束时写一次）。长时间批量任务应先确认
  批内代码数可控，或改造为分批落盘。
