# 预注册必须连"阈值是怎么来的"一起登记

## 适用场景

为前向观察、样本外验收、任何"看到结果后再解释"风险高的环节写预注册协议时。

## 现象

一份预注册看起来完整：指标定义了，阈值写了，中止条件列了。但事后复核时无法回答一个问题：

> 写这份协议时，**哪些数字已经是已知的**？

如果可用样本量在写协议时已经可见（因为数据地平线是确定的），那么"最少 40 个样本"
这个阈值到底是先验判断，还是照着已看到的 39 定出来的？**文件本身看不出来。**

## 根因 / 洞见

预注册的核心承诺是"规则先于结果"。但现实中常有一半信息先于规则：
**样本量往往可从数据边界推算，结果值不能**。

不披露这层区别，会产生两种隐性污染：

1. **阈值贴合已知样本**：把门槛设在"刚好高于当前样本"处，使首次判读必然落在
   EXPLORATORY，看起来严格，实则是为当前数据量身定做。
2. **事后调阈值**：样本长大后若结果不理想，把阈值"重新论证"一遍——因为原文没锁定。

## 推荐做法

1. 在合约里加一个显式字段，把**写协议时已知什么、未知什么**写清楚：

```json
"disclosure_sample_size_was_visible": {
  "statement": "可用标签日数(39)在写协议时已知，因为它由数据地平线和 20 日标签决定；IC 值未知。",
  "consequence": "最少 40 日的门槛恰好比可见的 39 高一点，读者有权知道。",
  "therefore": ["阈值按本日期锁定，不得事后调整", "首次判读按规则落到 EXPLORATORY，而非靠判断力通融"]
}
```

2. 让**代码**强制"先登记后运行"，而不是靠自觉。本项目 `bridge/forward_evaluation.py`
   读取 `status == "registered_before_results"`，不满足直接拒跑。
3. 强制降级逻辑写进代码而非写进文档：标签日低于门槛时，无论 IC 多漂亮都只能输出
   EXPLORATORY。文档可以不信，代码路径必须自己顶住。

## 验证依据

2026-10-18 首次前向判读：39 个标签日，IC 均值 0.12689、胜率 82.05%，四项 PASS 条件全满足、
七项 HALT 条件全未触发。若只按指标，结论会是"通过"；按预注册规则，结论是 **EXPLORATORY**。
代码路径确实顶住了——这正是该设计的验证。

同期还修掉一个相关缺陷：`np.bool_` 经 `json.dumps(default=str)` 会静默变成字符串
`"True"`，使布尔型判定字段在产物里类型不可靠。已在比较处逐项包 `bool()` 并补测试。

## 适用边界

- 若样本量与结果**同时**未知（例如真的在数据到齐前登记），这个披露字段应为 `null`，
  不要为了格式完整编一段话。
- 披露不等于放大样本。承认"39 太小"的正确做法是等数据，不是降低门槛。
