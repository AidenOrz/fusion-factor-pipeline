# 加速要有等价门，也要有诚实的收益测量

## 适用场景

把 Python 里的热点数值循环迁到 Rust（或其他编译语言）以提升研究迭代速度时。

## 现象

两件事同时发生，而且都很容易被掩盖：

1. **等价性没有验证。** 新实现"看起来"算的是同一件事，但排序并列值的处理、分母取前一日还是当日、
   退化截面的保护阈值——任一处不同，结果会安静地偏移，表现为"研究结论变了"而不是"报错了"。
2. **收益被假设而非测量。** 直觉上"Rust 一定更快"，但跨 FFI 的数据转换可能比计算本身更贵。

## 根因 / 洞见

**热点不在算法，在数据搬运。** 本项目实测：

| 核 | Rust | Python | 加速比 |
|---|---|---|---|
| 底部剔除（817 个截面 × 3,105 只） | 0.066s | 0.134s | **2.0x** |
| Spearman IC（200 个截面） | 0.049s | 0.130s | **2.7x** |
| 名单变更率（300 个集合 × 10 轮） | 0.062s | 0.041s | **0.67x（更慢）** |

第三个核更慢的原因是**接口设计**而非语言：Python 侧对每个日期调一次函数，
而 Rust 侧要先把 `Vec<Vec<String>>`（300 个字符串集合）跨边界转成 `HashSet`，
转换开销超过计算收益。同一份 Rust 代码，换个扁平数组 + 索引的接口就会快，
但**没实测之前不能这么声称**。

## 推荐做法

1. **先写纯 Rust 的可测核**，用 `#[cfg(test)]` 锁住易错语义（并列排名、分母方向）。
   本项目把 7 项语义测试放在 Rust 侧，不依赖 Python 也能跑 `cargo test`。
2. **Python 侧保留回退实现**，扩展缺失时自动降级。加速层成为硬依赖会让没有 Rust 工具链的机器无法复现。
3. **写一个 `verify_against_python()` 逐值比对门**，在上研究之前跑。本项目用 600 组随机用例：
   IC 最大差 2.22e-16、排名差 0.0、退化保护完全一致。**不一致就抛错，不许静默选快的那个。**
4. **用真实数据规模测收益**，并且把负结果也写进文档。一个"2.7x"和一个"0.67x"放在一起才是可信的报告。

## 验证依据

2026-10-19，`rust/fusion_accel/` + `bridge/accel.py`：cargo test 7 项通过、Python 10 项测试通过、
600 组随机用例等价，基准见 `runs/accel_benchmark_2026-10-19/benchmark.json`。

## 适用边界

- Windows 下 cargo 产出 `.dll`，Python 的 `spec_from_file_location` 不会据此推断扩展加载器（它只认 `.pyd/.so/.dylib`），
  必须显式构造 `importlib.machinery.ExtensionFileLoader`。
- 本机 cargo 的 `rsproxy.cn` 镜像**经系统代理不通**，需清掉 `HTTPS_PROXY` 才能拉取依赖；这与 git 需要代理正好相反。
- 等价门只证明"两条路径当前一致"，不证明任一实现符合论文定义。语义正确性仍需单独的测试与判读。
