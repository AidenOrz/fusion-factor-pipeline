# 因子库重算必须逐值对齐，且要喂全依赖列

## 适用场景

需要重算或补齐 alpha101 这类因子库的前向段时（原产物只到某日，或前向段有缺口）。

## 现象

三类失败都会静默发生，不会抛错：

1. 缺依赖列导致降级。只传 OHLCV 时，18 个行业/市值依赖因子全部走单一 UNKNOWN 桶的中性化分支，
   输出仍然是个数，但最大偏差可达 894。缺 cap 时个别因子直接失败，其余照常。
2. cs_scale 的正负 inf 相加变 NaN。cs_scale(x) = x / sum(|x|) 按日求和；
   若当日同时存在正 inf 与负 inf（ts_corr 在 194/817 天会产出），和为 NaN，整个截面作废。
   表现为某天所有股票都是空值，看起来像数据缺失，其实是算子层面的数值病理。
3. 横截面算子不能按股票分块。时间序列算子按 stock_code 分区，但 rank/cs_scale 按 trade_date 分区，
   必须全截面在场。按股票切分会让横截面排名变成只在子集内排名，结果错误且不报错。

## 推荐做法

1. 先对齐再使用。与权威源在重叠区逐值比对，要求 max abs diff = 0。本项目实测 106/107 因子精确一致，
   唯一发散项 alpha056 恰好不在冻结池内——这种恰好不影响必须被验证，不能假设。
2. 依赖列作为契约显式列出，缺列时主动抛错，而不是让中性化悄悄退化成单桶。
3. 求和前清洗 inf。对 cs_scale/rank 这类分母含聚合的算子，先 replace([inf,-inf], nan)。
4. 内存按因子维度分块（不是按股票），最终数值块一次性写出：16 GB 机器上
   2.57M 行 x 107 因子 x 8B 约 2.2 GB 可承受。注意 parquet 只能追加同 schema 的行组，
   分批追加不同列集必然报错。
5. 用独立实现交叉验证可疑列。本项目用 pandas 重写同一公式：独立实现前向 0 空日、存储文件 33 空日，
   才能确定是文件缺陷而非因子本身稀疏。

## 验证依据

2026-10-19，artifacts/recompute_alpha101.py：107 因子在 2,567,271 行上重算，与权威源 1,968,826 行重叠
106/107 逐值一致（max abs diff = 0）；补上 industry+cap 前，18 个行业依赖因子最大偏差 894；
alpha028 修复 inf 求和后前向覆盖 44.06% 升至 99.94%，全窗空日 4 降至 0。

## 适用边界

- 逐值对齐只在同一面板、同一依赖列口径下可期待。换了市值或行业来源，先重新对齐再谈复现。
- alpha056 这类依赖 cap 的因子若市值口径不同会长期不一致；若它不在冻结池内，记录排除理由比强行修更重要。
- 清洗 inf 会改变数值（把本可传播的 inf 变 null），须在 manifest 记录，且该处理不应在历史段与冻结结果上重放。
