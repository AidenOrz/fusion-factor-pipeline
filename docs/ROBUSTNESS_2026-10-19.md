## 0. 先回答那句质询：是不是"差一天"

**算术上是的，但它不是一个准确的说法，我不应该那样讲。**

实测：面板最后一个交易日 2026-10-16，最后一个可标签日 2026-09-10，其出场日正好是 2026-10-16。
要让 2026-09-11 变成可标签日，需要它的出场日 = 2026-10-19（下一个交易日）。所以"再补 1 个交易日行情"
确实能把标签日从 39 推到 40。

**但这个表述有三处误导**：

1. **它把"日历可得"说成了"判读可得"。** 2026-10-19 不是"再来一天"，它是**下一轮数据刷新**——
   需要再接一次 baostock、重跑面板延伸、重算标签。周期由数据什么时候到决定，不由我决定。
2. **它暗示"到了 40 就水到渠成"，这是错的。** 40 只是脱离 EXPLORATORY 的门槛。PASS 还要四条同时成立；
   250 天才是晋级门槛。40 天的判读样本量仍然极小、标签高度重叠，**通过也不构成任何 alpha 声明**。
3. **它把注意力从真正该看的地方引开了。** 真正的问题不是"还差几天"，而是下面第 3 点：这 39 天本身就在顺风窗里。

正确说法：**再补 1 个交易日的行情即可进入规则允许的判读区（40 天），但那只是一次"允许判读"，不是"能够通过"。**

## 1. 换手率偏高：先纠正一个口径错误，再解释差额

### 1.1 0.5267 与 0.3805 不是同一个指标

这是我上一轮留下的问题，必须先纠正：

| | 值 | 定义 |
|---|---|---|
| 我上一轮报告的"前向 0.5267" | 0.5267 | **保留率** = \|prev ∩ cur\| / \|prev\| |
| C 轨 `mean_daily_change_rate` | 0.3805 | **变更率** = 1 − 保留率 |

两者是互补数，直接并列会得出"0.53 对 0.38"这种夸大 2.4 倍的错觉。

**同口径重算**（同一套剔除逻辑、同一分母）：

| | 变更率 | 保留率 | 观测数 |
|---|---|---|---|
| 历史 C 轨（2024-10-22~2025-12-03） | **0.3805** | 0.6195 | 273 |
| 前向（2026-07-20~10-16） | **0.4733** | 0.5267 | 58 |

差额 **+0.0928**。注意历史值 0.3805 是用同样代码在冻结面板上重算的，与 C 轨存档值逐位一致，
说明口径对齐无误。

### 1.2 差额的 97.5% 来自分母变小，不是评分器变不稳定

用户猜的两个方向（小盘波动大 / 接缝后 universe 构成变化）里，**第二个方向对，但不是"构成"变了，而是"规模"变了**。

决定性证据——**绝对换手只上升 6.3%，而尾部规模缩小 14.6%**：

| | 历史 | 前向 | 比值 |
|---|---|---|---|
| 每日实际进出的只数 | 72.2 | 76.7 | **1.063** |
| 尾部规模（只） | 189.7 | 162.0 | **0.854** |
| 隐含变更率 | 72.2/189.7 = 0.3805 | 76.7/162.0 = 0.4736 | 1.063/0.854 = **1.245** |

**反事实验证**：把历史尾部随机二次抽样到前向的尾部规模（162 只），重复 50 次，
历史变更率变成 **0.4710（sd 0.0013）**，与前向 0.4733 仅差 **0.0023**。

即：把两边的分母对齐之后，**前向换手与历史几乎完全一样**。0.38→0.47 的落差是算术效应，
不是行为变化。

### 1.3 顺带确认：尾部变小正是覆盖缺口造成的

尾部规模 189.7 → 162.0 与 B2 域 1,851 → 1,585 的收缩同源，而后者是取数假象（见第 2 点）。
**所以换手率偏高与覆盖缺口是同一个根因的两个表现。**

### 1.4 已预注册"历史一致"的容差口径（这一步必须在正式判读前做）

晋级门槛原文只写了"换手率与历史 C 轨一致"，没说一致到什么程度。若等正式判读出结果再定义，
就是临场裁量。所以本轮**已写入预注册** `config/forward_observation_prereg_2026-10-18.json`：

```json
"turnover_consistency_operationalisation": {
  "decision_rule": {
    "primary_comparison": "tail-size-matched churn",
    "tolerance_absolute": 0.05,
    "tolerance_relative": 0.15,
    "secondary_comparison": "absolute names swapped per day",
    "secondary_tolerance_relative": 0.20
  }
}
```

按该规则，当前状态：\|0.4733 − 0.4710\| = **0.0023 ≤ 0.05 → PASS**。

**边界**：这不是放松门槛，而是把门槛的度量方式固定下来。若将来看似匹配后仍超差，门槛照样不过。
同时列出失效条件：尾部规模 materially 变化、剔除比例改变、或 558 只代码被补齐（补回后尾部变大，率会机械性下降）。

## 2. 覆盖缺口：旧说法是错的，必须撤回

### 2.1 HANDOFF 里"多为长期停牌或退市"的说法不成立

上一轮我写过"561 只在 07-24 后完全没有数据……多为长期停牌或退市"。**这句话是错的，现予撤回。**

对 561 只**逐只查询上游 baostock**（2026-07-27~10-16）：

| | 只数 | 占比 |
|---|---|---|
| 上游**有完整数据**（可补） | **558** | **99.5%** |
| 上游确实无数据 | **3** | 0.5% |

真无数据的只有 `000004`、`002808`、`002898`。

### 2.2 三条互相独立的证据都指向"取数假象"

1. **市值分布完全均匀**：561 只的流通市值分位在 10 个十分位上是 55/56/55/56/55/56/55/56/55/56。
   真实的停牌退市必然偏向小市值或 ST，**均匀分布是随机抽取的特征**。
2. **交易所归属完全分裂**：沪市 `600/601/603/605` 四个前缀**丢失 0 只**；深市 `000` 前缀**丢失 74.1%**。
   市场不会按代码前缀停牌，取数会。
3. **ST 占比只有 5.9%**，与全市场 ST 比例相当，没有富集。

### 2.3 覆盖缺口对域规模的影响（用户要的那一行）

| | 值 |
|---|---|
| 接缝前 B2 日均 | 1,851 |
| 接缝后 B2 日均（实测） | 1,585 |
| 落差 | 267 |
| 其中 558 只是 B2 成员 | **360** |
| 若补齐后 B2 估算 | **≈1,945** |

**结论：B2 从 1,851 降到 1,585 不是真实的域收缩，而是取数造成的缺口。** 补齐后 B2 会回到接缝前水平。

这有三个直接后果：

- HALT 的"不足 500 只"地板从未接近（最低 1,579），所以**这个保护没有起作用，也无须起作用**；
- **跨接缝比较域规模是无效的**，任何"前向域变小了"的表述都必须标注为假象；
- 前向 IC 是在一个**丢掉了约 18.5% 成员**的 B2 域上算的（360 / 1,945）。由于缺失按代码前缀
  而非按特征聚类，它更像随机缺失而非选择偏差，但这一点只能靠"市值十分位均匀"间接支持，
  不是一个定理——**前缀本身可能与其他属性相关，我没有排除这种可能**。

**未修复**：本轮只诊断，不补齐。补齐 558 只需要重跑取数与面板延伸，属于下一轮的工作量。

## 3. 首份正式判读恰逢顺风窗：这一点无法用统计解决

用户的判断是对的，而且我同意它比"还差一天"重要得多。

实测约束：前向 39 个标签日全部落在 2026-07-20 ~ 2026-09-10。这期间**连剔除组都是 +1.13% 超额**，
留存组 +3.92%、正超额交易日占比 100%。这是一个明确的单边上行窗。

协议里能做的都已经做了：

- 要求前后半窗同号（实测前半 0.083 / 后半 0.169，同号）；
- 预注册了 HALT 条件，包括 \|IC\| > 0.40 视为泄漏或 bug；
- 固定了"不得因某日 IC 不利而删除该日"。

**但协议不能做的事**：它无法把顺风窗变成逆风窗。IC 0.127 是在友好 regime 下取得的，
**下一份判读大概率仍在同一窗内**（因为标签日只能逐日向前推进，不可能跳到另一个 regime）。

因此这条必须写进正式判读模板：**PASS 只证明"评分器在这段行情里没有失效"，不证明它在别的行情里有效。**
真正的检验是等这个窗口结束、市场状态切换之后的表现——那需要时间，不需要更多分析。

## 4. horizon 敏感性（补齐项 1）

用**冻结预测**（不重训、不换种子）计算同一入场日、持有 20/40/60 个交易日的 IC：

| horizon | 标签日 | 平均 IC | IC 标准差 | 胜率 | 相对 20 日 |
|---|---|---|---|---|---|
| **20** | 254 | 0.12015 | 0.15137 | 81.10% | 1.000 |
| **40** | 234 | 0.13480 | 0.12867 | 84.62% | **1.122** |
| **60** | 214 | 0.13330 | 0.09116 | 95.79% | **1.110** |

**判读**：IC 从 20 日到 40 日**没有衰减**，反而略升。

**但必须说清楚这不是"40 日更好"**：

1. 同一入场日下，40 日收益**在数学上包含**20 日收益，两者高度相关。这是持久性描述，不是独立性检验。
2. 标签日数随 horizon 递减（254→234→214），40/60 日的样本尾部天然更短。
3. **结论不得用于更换标签 horizon**。冻结配置仍是 20 日，更换属"新一轮完整预注册"（HANDOFF §2 决策 4）。

能得到的唯一实质结论：**信号不是 20 日窗口的一次性产物，在 21–40 日仍有排序能力**。
这降低了"20 日后失效"的风险，但不能反过来证明更长持有更优。

## 5. Rust 加速（用户要求"密集计算改用 rust"）

### 5.1 做了什么

`rust/fusion_accel/` 是一个独立 crate，提供 4 个横截面热点核：底部剔除标记、Spearman IC、
名单变更率、平均排名。设计上**不读文件、不持有管道状态**，Python 侧保留全部决策权。

Python 侧 `bridge/accel.py` 是**可选加速层**：扩展不存在时自动回退纯 Python，不影响可运行性。

### 5.2 等价性（这是前提，不是附属）

`verify_against_python()` 用 **600 组随机用例**逐一比对两条路径：

| 项 | 结果 |
|---|---|
| 用例数 | 600 |
| IC 最大绝对差 | **2.22e-16**（机器精度） |
| 排名最大绝对差 | **0.0** |
| 退化保护一致性 | 完全一致 |

另有 7 项 Rust 单元测试 + 10 项 Python 测试锁定行为（含"并列值取下一位"与"分母用前一日"两条易错点）。

### 5.3 性能（实测，如实报告）

817 个横截面 × 平均 3,105 只：

| 核 | Rust | Python | 加速比 |
|---|---|---|---|
| 底部剔除 | 0.066s | 0.134s | **2.0x** |
| Spearman IC | 0.049s | 0.130s | **2.7x** |
| 名单变更率 | 0.062s | 0.041s | **0.67x（更慢）** |

**变更率反而更慢了**，原因很明确：该核当前 Python 实现是对每个日期调一次函数，
Rust 侧却要先把整个 300 个集合的 `Vec<Vec<String>>` 跨 FFI 转成 `HashSet`，
转换开销超过计算收益。**这是一个真实的负面结果，不隐藏。**

补救方向（未做）：对长序列应该一次性传扁平数组 + 索引，而不是嵌套字符串向量。
在修好之前，**本项目不声称"密集计算已全面迁移到 Rust"**，只声称三个核中的两个确有收益。
