# 大规模计算的内存优化（2026-10-19）

> 触发：用户报告本机 16 GB 内存吃满、CPU 却闲置。
> 结论先行：**瓶颈不是算力，是 pandas 在每个变换步骤复制整张宽表**。
> 优化后的主杠杆是**列投影**（实测 19.4 倍），不是多进程也不是更快的语言。

## 1. 机器与现象

| 项 | 值 |
|---|---|
| 物理内存 | **15.7 GB**（8+8 GB @4800） |
| 逻辑核心 | **20** |
| 页面文件 | 15.9 GB，当前占用 123 MB |

"内存吃满但 CPU 空转"这个组合只有一个解释方向：进程在**换页**，而不是在计算。
CPU 在等磁盘，所以利用率低；内存被常驻工作集占满，所以报警。

## 2. 实测：钱花在哪一步

对真实的重型步骤（前向标签重建）逐阶段采样 RSS：

| 阶段 | RSS |
|---|---|
| 进程启动 | 84 MB |
| **读取全部 185 列** | **7,631 MB** |
| 释放后 | 4,361 MB |
| **只读标签需要的 11 列** | **580 MB** |
| 再做一次 merge | 620 MB |

同一份数据，两个读法差 **13 倍峰值**；单纯看 DataFrame 体积也差 **19.4 倍**
（3,910 MB vs 202 MB）。

**这就是答案**：`pd.read_parquet(path)` 不带 `columns` 时，会把 180 列的宽表整张读进内存，
然后每个变换（merge、assign、concat）再复制一次。一张表同时活着 2–3 份，16 GB 就没了。

## 3. 三个杠杆与实测收益

### 3.1 列投影（主杠杆）

| 读法 | 列数 | 内存 | 相对全量 |
|---|---|---|---|
| 全列 | 180 | 2,767 MB | 1.00 |
| 投影到 42 列（37 特征 + 5 身份） | 42 | **629 MB** | **0.23（省 4.4 倍）** |

投影是**免费**的：parquet 是列式存储，未请求的列根本不会被解压。
这也是为什么它比任何"更快的语言"都更值钱——它消除工作，而不是加速工作。

### 3.2 行组流式读取

冻结面板只有 **2 个 row group**，所以流式读取的峰值就等于半个文件（335 MB，
是全量的 12.1%）。行组太大，流式的价值发挥不出来。

因此新增 `write_panel(..., row_group_size=250_000)`：同样 50 万行，写成 **5 个行组**。
**下次重物化面板时应用这个写法**，流式能力才真正可用。

### 3.3 类别 dtype

对 `panel_fusion_full_market` 实测：`universe_version`(79.8 MB)、`panel_scope`(46.0 MB)、
`name`(45.7 MB)、`industry`(44.6 MB)、`ts_code`(41.1 MB)、`code`(33.9 MB) 六个字符串列
合计约 **291 MB**，都是低基数字典型数据。

但**在已投影的帧上实测节省为 0 MB**——因为投影后这些列大多没被读进来。
**诚实结论：类别 dtype 是"读全量时"的补救，不是主杠杆。** 先投影，再谈 dtype。

## 4. 落地的代码

`bridge/memory.py`：

| 函数 | 作用 |
|---|---|
| `read_panel(path, columns, shrink_strings)` | 投影读取 + 可选类别压缩 |
| `iter_row_groups(path, columns)` | 逐行组流式，峰值 = 一个行组 |
| `write_panel(frame, path, row_group_size)` | 小行组写盘，让流式真正可用 |
| `shrink(frame)` | 低基数列转 category，**列近唯一时不转**（转了反而更大） |
| `release(*frames)` | 阶段之间清引用并 gc，降低峰值 |
| `estimate_projection(path, columns)` | 不加载数据就估算投影后的内存 |

已接入真实路径：`bridge/forward_labels.py`、`bridge/forward_scoring.py` 的读取改为投影读。

**刻意没做的事**：没有把 float64 自动降为 float32。那是真实的数值变化，
必须显式选择并测量误差，不能作为默认行为。

## 5. 下一轮大规模计算的建议顺序

1. **先列投影，永远**。写任何脚本前先问"这个计算真的需要这 180 列吗"。
   本项目最重的几个脚本都只需要 11–42 列。
2. **重物化面板时用小行组写**（`write_panel`），否则流式形同虚设。
3. **阶段之间显式 `release`**，不要让两张宽表同时活着。
4. **CPU 并行放最后**。当峰值内存降到 600 MB 量级、不再换页时，LightGBM 的
   `n_jobs` 与多进程才有意义；在此之前加核心只会加剧换页。
5. 若仍需更大规模，再考虑 polars / Rust——**但先证明瓶颈是计算而不是内存搬运**。
   本次实测证明当前算例的瓶颈是后者。

## 6. 与 Rust 加速的关系（避免误会）

上一轮的 Rust 核（底部剔除 2.0x、Spearman IC 2.7x）解决的是**另一个问题**：
横截面内循环的常数因子。它**不解决**内存峰值。

两者不冲突，但优先级明确：**内存换页时，2.7 倍的单核加速几乎被等待磁盘吃光**。
所以顺序是先把峰值降下来，再谈算力。
